# preprocessing.py — Модуль предобработки данных

## Назначение

Модуль выполняет полный цикл первичной обработки сырых событий маркетплейса: от парсинга составных полей до нормализации контактных данных. На выходе — чистый датафрейм, готовый к агрегации профилей.

## Основные возможности

- **Парсинг составных полей** — извлечение признаков из JSON-строк (`realtime_features`) и массивов (`fs_features`, `non_processing_features`) в отдельные колонки.
- **Очистка данных** — удаление полных дубликатов строк.
- **Унификация разметки** — исправление profile_id, у которых в разных событиях указаны разные entity_id (берётся актуальное значение из последнего события).
- **Нормализация контактов** — приведение email, телефонов, имён и фамилий к единому формату, извлечение доменов и префиксов.

## Архитектура
```text
full_preprocessing(df)
│
├── Шаг 1: extract_array_features(df, "fs_features")
├── Шаг 2: extract_array_features(df, "non_processing_features")
├── Шаг 3: extract_json_features(df, "realtime_features")
├── Шаг 4: df.drop_duplicates()
├── Шаг 5: unify_entity_ids(df)
├── Шаг 6: normalize_contacts(df)
│
└── Чистый датафрейм
```

## Состав функций

| Функция | Назначение | Вход → Выход |
|---|---|---|
| `parse_array_like_features` | Парсинг массива строк `key:value` или `flag` в словарь |
| `json_unpack` | Безопасная распаковка JSON-строки с обработкой ошибок |
| `extract_array_features` | Извлечение признаков из array-like колонки в плоские колонки |
| `extract_json_features` | Извлечение признаков из JSON-колонки в плоские колонки |
| `unify_entity_ids` | Исправление profile_id с несколькими entity_id (берётся последнее по времени) |
| `normalize_email` | Нижний регистр, удаление пробелов, валидация `@` |
| `extract_email_domain` | Извлечение доменной части email |
| `normalize_phone` | Очистка до цифр, приведение к `79XXXXXXXXX` |
| `extract_phone_prefix` | Извлечение кода страны + первых 3 цифр оператора |
| `normalize_name` | Стрип, lower case, удаление спецсимволов (кроме дефиса и апострофа) |
| `normalize_contacts` | Применение всех нормализаций к датафрейму (email, phone, имена) |
| `full_preprocessing` | Полный пайплайн предобработки с логированием каждого шага |

## Ключевые особенности реализации

- **Модульность:** каждая функция выполняет одну задачу и возвращает DataFrame (pipeline-friendly).
- **Логирование:** каждый из 6 шагов логируется с указанием изменений (количество строк, колонок, аномалии).
- **Безопасность:** все функции работают с копиями данных, оригинал не модифицируется.
- **Обработка ошибок:** JSON-парсинг и нормализация контактов корректно обрабатывают `None`, пустые строки и невалидные значения.
- **Детерминированность:** все преобразования воспроизводимы и не зависят от порядка строк.

# aggregation_profiles.py — Модуль агрегации паспорта профиля

## Назначение

Модуль собирает "золотую" таблицу профилей из очищенных событий. Каждая строка — один уникальный `profile_id` со всей накопленной историей: демография, контакты, флаги, счётчики.

## Основные возможности

- **Агрегация демографии** — последнее непустое значение имени, пола, гео, дня рождения.
- **Сбор контактных множеств** — все email'ы, телефоны, устройства, браузеры за всю историю профиля.
- **Вычисление флагов** — был ли профиль хоть раз is_gmail, is_man, is_phone и т.д.
- **Подсчёт счётчиков** — количество событий, уникальных email'ов, телефонов, устройств.

## Архитектура
```text
build_profiles_df(df_clean)
│
├── 1. Сортировка событий по created_at
├── 2. Группировка по profile_id
│ ├── Группа А: last / last_non_null (демография)
│ ├── Группа Б: frozenset (контактные множества)
│ ├── Группа В: max (флаги)
│ └── Группа Г: first (entity_id, entity_type)
├── 3. Счётчики (n_events, n_emails, n_phones, n_devices)
├── 4. Приведение типов (булевы флаги)
│
└── profiles_df
```

## Структура результата

| Группа | Колонки | Стратегия | Пример |
|---|---|---|---|
| А: Демография | first_name_clean, sex, geoname_id, birthday, tz_offset, ... | Последнее непустое | `"александр"` |
| Б: Контакты | email_normalized, phone_normalized, device, browser, ... | `frozenset` всех значений | `{"a@mail.ru", "b@gmail.com"}` |
| В: Флаги | is_gmail, is_man, is_woman, was_phone_lead, ... | `True` если был хоть раз | `True` |
| Г: Служебные | entity_id, entity_type | Первое значение | `"E42"`, `"multi_profile"` |
| Счётчики | n_events, n_emails, n_phones, n_devices | Количество | `3`, `2`, `1`, `2` |

## Результаты на реальных данных

| Параметр | Значение |
|---|---|
| Профилей | 472 106 |
| Колонок | 33 |
| Среднее событий на профиль | ~2.0 |
| Multi-entity профилей | 7 485 |
| Время агрегации | ~169 сек (pandas) |

## Ключевые особенности

- **frozenset для множеств** — иммутабельный, хешируемый, поддерживает операции `&` и `|`.
- **Два типа агрегации:** `"last"` для стабильных полей (быстро), `last_non_null` для редких (надёжно).
- **Приведение типов:** булевы флаги из JSON-строк → `bool`.

## Зависимости

`pandas`, `logging`

# site_activity_processor.py — Модуль построения индекса сайтов

## Назначение

Модуль строит "цифровой след" каждого профиля — словарь, где для каждого `profile_id` хранятся множества посещённых сайтов по категориям. Это ключевой источник поведенческих признаков для матчинга.

## Основные возможности

- **Сбор site_id по категориям** — has_account, visited_30, has_order_365 и ещё 9 категорий.
- **Динамическое определение категорий** — не хардкодит список, а находит все колонки с site-признаками.
- **Объединение всех сайтов** — поле `_all` для быстрых проверок "пересекались ли профили хоть где-то".
- **Безопасное преобразование** — site_id конвертируются в `int` с защитой от невалидных значений.

## Архитектура
```text
build_site_index(df_clean)
│
├── 1. Определение категорий (динамически по префиксам)
├── 2. Инициализация словаря для каждого profile_id
├── 3. Заполнение по категориям:
│ └── groupby profile_id -> set(site_id) -> int
├── 4. Построение _all = union всех категорий
│
└── site_index
```
## Структура результата

```python
site_index = {
    "p1": {
        "has_account": {2046, 5801},
        "visited_30": {3130, 2046, 5801},
        "has_order_30": {3130},
        # ... ещё 9 категорий
        "_all": {2046, 5801, 3130}  # union
    },
    "p2": { ... }
}
```

## Зависимости
pandas, logging

# cat_activity_processor.py — Модуль построения индекса почтовой активности

## Назначение

Модуль строит индекс почтовых реакций каждого профиля — словарь, где для каждого `profile_id` хранятся множества значений по категориям email-коммуникаций. Это дополнительный источник признаков для матчинга.

## Основные возможности

- **Сбор почтовых реакций по категориям** — postman_response, postman_action, postman_campaign, postman_scenario, mm_event.
- **Динамическое определение категорий** — автоматически находит все колонки с почтовыми признаками.
- **Нормализация значений** — приведение к нижнему регистру, удаление пробелов.
- **Объединение всех реакций** — поле `_all` для быстрых проверок.

## Архитектура
```text
build_cat_index(df_clean)
│
├── 1. Динамический поиск категорий (по префиксам)
├── 2. Инициализация словаря для каждого profile_id
├── 3. Заполнение по категориям:
│ └── groupby profile_id -> set(str) с нормализацией
├── 4. Построение _all = union всех категорий
│
└── cat_index
```

## Структура результата

```python
cat_index = {
    "p1": {
        "postman_response_90": {"ok", "clicked"},
        "postman_action_30": {"delivered"},
        "mm_event_30": {"campaign_1", "campaign_2"},
        # ... ещё категории
        "_all": {"ok", "clicked", "delivered", "campaign_1", "campaign_2"}
    },
    "p2": { ... }
}
```
## Зависимости
`pandas`, `logging`

# profiles_processor.py — Единая точка входа для обработки профилей

## Назначение

Модуль объединяет все этапы обработки профилей в один вызов. Принимает сырые данные, возвращает три структуры, готовые для дальнейших этапов: Blocking, Feature Engineering и моделирования.

## Основные возможности

- **Единый вызов** — `process_profiles(df_raw)` запускает весь пайплайн.
- **Последовательное выполнение** — предобработка → паспорт → индекс сайтов → индекс почтовой активности.
- **Логирование каждого этапа** — видно, что происходит и сколько времени занимает.
- **Согласованность** — все три структуры используют один набор `profile_id`.

## Архитектура
```text
process_profiles(df_raw)
│
├── Этап 1/4: full_preprocessing(df_raw)
│ └── preprocessing.py
├── Этап 2/4: build_profiles_df(df_clean)
│ └── aggregation_profiles.py
├── Этап 3/4: build_site_index(df_clean)
│ └── site_activity_processor.py
└── Этап 4/4: build_cat_index(df_clean)
└── cat_activity_processor.py
│
└── (profiles_df, site_index, cat_index)
```

## Использование

```python
from profiles_processor import process_profiles

profiles_df, site_index, cat_index = process_profiles(df_raw)
```
## Зависимости
`preprocessing`, `aggregation_profiles`, `site_activity_processor`, `cat_activity_processor`, `logging`
