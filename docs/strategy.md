# Стратегия системы матчинга и дедупликации профилей клиентов

## 1. Общая архитектура решения

Система строится по классическому пайплайну Entity Resolution:
 ```text
Сырые события
│
▼
Предобработка и нормализация
│
▼
Агрегация событий → "Золотые" профили
│
▼
Blocking (предварительный отсев пар)
│
▼
Feature Engineering (признаки сходства пар)
│
▼
Модель матчинга (бинарная классификация пар)
│
▼
Кластеризация (Connected Components + постобработка)
│
▼
Определение порогов автообъединения / ручной проверки
│
▼
Демонстрационный интерфейс (Streamlit)
 ```

## 2. Результаты EDA (ключевые выводы)

### 2.1 Структура данных

- После парсинга полей удалено **18 полных дубликатов**.
- **472 106** уникальных профиля (`profile_id`).
- **Single profile**, среднее число событий: **2**.
- **Multi profile**, среднее число событий: **3.5**.
- Почти у **100%** профилей есть хотя бы один `email` в истории.

### 2.2 Целевая переменная (entity)

- **95%** профилей — `single_profile` (один профиль на человека).
- **5%** профилей — `multi_profile` (несколько профилей на человека).
- В `multi-entity`:
  - 6 768 сущностей по 2 профиля,
  - 305 по 3,
  - 25 по 4,
  - 3 по 5,
  - 3 по 6,
  - 1 по 8,
  - 2 по 14,
  - 1 по 19.

**Вывод:** задача решается преимущественно попарным сравнением. Наличие крупных entity (8, 14, 19 профилей) требует качественной кластеризации связных компонент, поскольку ошибка на одном ребре может развалить большой кластер.

### 2.3 Аномалии и их обработка

- Обнаружено **102 profile_id** с разными `entity_id` в разных событиях (результат перепривязки профиля задним числом — система обнаружила дубликат и перенесла профиль из `single_profile` entity в `multi_profile` entity).
- **Исправлено:** для каждого `profile_id` взят актуальный `entity_id` из последнего по времени события. После коррекции все `profile_id` имеют строго один `entity_id`.

### 2.4 Качество полей

| Поле | Заполненность | Роль в решении |
|---|---|---|
| `email` | ~100% | Ключевой блокировочный признак |
| `phone` | ~10% | Дополнительный блокировочный ключ, высокая точность |
| `first_name` | ~36% | Вспомогательный признак |
| `last_name` | ~4% | Вспомогательный признак |
| `birthday` | <1% | Точное совпадение — сильный сигнал |
| `fs_features` (сайтовые) | ~100% | Мощный поведенческий сигнал для активных профилей |

## 3. Предобработка и нормализация

### 3.1 Парсинг составных полей

- `fs_features`: извлечение site-id в отдельные множества по категориям, бинарные флаги, категориальные значения.
- `non_processing_features`: device, osfamily, browser.
- `realtime_features`: гео-признаки, временные метки.

### 3.2 Удаление дубликатов и аномалий

- Удаление полных дубликатов строк.
- Унификация `entity_id` для профилей с несколькими значениями (по последнему событию).

### 3.3 Нормализация контактных данных

- **Email:** приведение к нижнему регистру, выделение домена.
- **Телефон:** приведение к единому формату (только цифры), выделение кода страны и префикса оператора.
- **Имя/фамилия:** приведение к нижнему регистру, удаление лишних пробелов.

## 4. Агрегация до "золотых" профилей

**Принцип:** одна строка = один `profile_id` со всей накопленной историей.

### 4.1 Стратегия агрегации по типам полей

| Группа полей | Стратегия |
|---|---|
| `entity_id`, `entity_type` | Первое значение (одинаково для всех событий) |
| `first_name`, `last_name`, `sex`, `birthday` | Последнее непустое значение по `created_at` |
| `email`, `phone` | **Множество всех уникальных значений** за всю историю |
| `device`, `osfamily`, `browser` | Множество уникальных значений |
| `geoname_id`, `tz_offset`, `population` | Последнее непустое значение |
| `local_hour`, `day` | Среднее или мода |
| Сайтовые `fs_features` (has_account, visited_30, ...) | Множество site_id по каждой категории + общий union |
| Флаги `fs_features` (is_gmail, is_man, ...) | `True`, если встречался хотя бы раз |
| Категориальные `fs_features` (postman_response_90, ...) | Множество уникальных значений |

### 4.2 Дополнительные счётчики

- Количество уникальных email'ов, телефонов, устройств, браузеров.
- Количество уникальных site_id в истории.
- Количество событий профиля, временной диапазон активности.

## 5. Blocking (предварительный отсев пар)

### 5.1 Цель
Сократить количество попарных сравнений с ~111 миллиардов (все возможные пары 472K профилей) до обозримого числа, **не потеряв реальные дубликаты**.

### 5.2 Стратегия: многопроходный blocking

| Проход | Ключ блокировки | Обоснование |
|---|---|---|
| Pass 1 (жёсткий) | Точное совпадение любого email | Покрытие ~100%, детерминированная анонимизация гарантирует совпадение |
| Pass 2 (жёсткий) | Точное совпадение телефона | Покрытие ~10%, но высокая точность |
| Pass 3 (мягкий) | Token Blocking по имени + совпадение гео (geoname_id) | Устойчив к опечаткам в имени: "Александр" и "Александра" попадут в один блок через общий токен |
| Pass 4 (поведенческий) | Пересечение по site_id | Для активных профилей с rich history, включая бесконтактные |
| Pass 5 (дополнительный) | Совпадение osfamily + device + browser + geoname_id | Слабый catch-all для оставшихся профилей |

**Token Blocking (Pass 3):** разбивает имя на токены-слова и создаёт блоки по каждому токену. Например, профиль с именем "Анна-Мария" попадёт в блоки `["анна", "мария"]`, что позволяет найти дубликаты с опечатками, сокращениями и разным порядком слов. Токены очищаются от стоп-слов и спецсимволов.

Все кандидаты из разных проходов объединяются (union). Это гарантирует, что ни один профиль не останется без шанса на матчинг.

### 5.3 Meta-blocking (опциональная фильтрация)

После генерации пар из всех проходов применяется meta-blocking:

- Строится граф: профили — вершины, рёбра — пары-кандидаты.
- Вес ребра = количество blocking-проходов, в которых встретилась данная пара.
- Рёбра с весом = 1 (пара встретилась только в одном проходе) отсекаются.

**Эффект:** снижение количества пар-кандидатов в 2-3 раза, повышение Precision blocking'а без потери Recall.

### 5.4 Метрика качества blocking'а
- **Blocking Recall** — доля истинных пар (из одной entity), попавших хотя бы в один blocking-проход.
- **Целевое значение:** > 0.99.
- Метрика замеряется на train-выборке.

## 6. Feature Engineering

Для каждой пары профилей (A, B) — как положительных (из одной entity), так и отрицательных — вычисляются признаки сходства.

### 6.1 Строковые сходства

| Признак | Метод |
|---|---|
| Сходство имени | Расстояние Левенштейна (нормализованное), Jaccard по триграммам |
| Сходство фамилии | Аналогично имени |
| Сходство email (локальная часть) | Левенштейн, Jaccard |
| Совпадение домена email | Точное совпадение (1/0) |
| Оба email на популярных доменах | Оба gmail, оба yandex, разные публичные домены |

### 6.2 Телефонные признаки

| Признак | Описание |
|---|---|
| Полное совпадение телефона | Хотя бы одна пара из множеств совпадает |
| Совпадение префикса | Код страны + 3 цифры оператора |
| Доля совпадающих цифр | Посимвольное сравнение |

### 6.3 Гео-признаки

| Признак | Описание |
|---|---|
| Совпадение geoname_id | Точное совпадение города |
| Совпадение страны | Если доступно |
| Расстояние между городами | Если доступны координаты |

### 6.4 Поведенческие признаки (fs_features) — ключевое преимущество

| Признак | Формула |
|---|---|
| Jaccard has_account | \|A ∩ B\| / \|A ∪ B\| |
| Jaccard visited_30 | \|A ∩ B\| / \|A ∪ B\| |
| Jaccard visited_365 | \|A ∩ B\| / \|A ∪ B\| |
| Jaccard all_sites (union) | \|A_all ∩ B_all\| / \|A_all ∪ B_all\| |
| Overlap count (абсолютное) | \|A_all ∩ B_all\| |
| Overlap ratio A | \|A ∩ B\| / \|A\| |
| Overlap ratio B | \|A ∩ B\| / \|B\| |
| Has rare site overlap | 1, если в пересечении есть site_id с IDF > порога |
| IDF-weighted overlap | Σ IDF(site_id) по пересечению |

### 6.5 Признаки на основе флагов

| Признак | Описание |
|---|---|
| both_is_gmail | Оба профиля используют Gmail |
| both_is_yandex | Оба профиля используют Yandex |
| gender_match | Пол указан и совпадает |
| gender_conflict | Пол указан и различается (сильный отрицательный сигнал) |
| both_is_phone | Оба профиля имеют телефон |
| both_was_phone_lead | Оба профиля были телефонным лидом |

### 6.6 Категориальные сходства

| Признак | Метод |
|---|---|
| postman_response_90 | Jaccard множеств значений |
| postman_action_30/90 | Jaccard + точное совпадение |
| postman_campaign_30/90 | Jaccard |
| postman_scenario_30/90 | Jaccard + точное совпадение |
| mm_event_30/90 | Jaccard |

### 6.7 Демографические и временные признаки

| Признак | Описание |
|---|---|
| Совпадение birthday | Точное совпадение полной даты |
| Совпадение года рождения | Если полная дата недоступна |

## 7. Модель матчинга

### 7.1 Выбор подхода

**Градиентный бустинг (CatBoost/LightGBM)** — бинарная классификация пар профилей.

**Обоснование:**
- Отлично работает с табличными признаками.
- Встроенная обработка пропусков.
- Интерпретируемость (feature importance).
- Высокая скорость обучения на сотнях тысяч пар.
- Не требует GPU для обучения.

### 7.2 Подготовка обучающей выборки

- **Положительные пары:** все пары профилей из одной multi-entity.
  - Оценка количества: ~6 768 × 1 + ~305 × 3 + ~25 × 6 + ... ≈ **~18 000 положительных пар**.
- **Отрицательные пары:** профили из разных entity, прошедшие blocking + дополнительный random negative sampling.
- **Соотношение positive:negative** = 1:3 или 1:5 (подбирается на валидации).
- **Разбиение:** train / val / test = 60% / 20% / 20% (уже задано на уровне entity_id — все профили одной entity попадают только в один набор).

### 7.3 Метрики качества (на уровне пар)

- **Precision** — доля правильно предсказанных дубликатов среди всех предсказанных.
- **Recall** — доля найденных дубликатов среди всех реальных.
- **F1** — гармоническое среднее Precision и Recall.
- **ROC-AUC** — для оценки качества модели до выбора порога.

### 7.4 Подбор порога

- Анализ Precision-Recall кривой на валидации.
- Выбор оптимального порога по F1 или по бизнес-требованиям (минимизация false positives для автообъединения).

## 8. Кластеризация и постобработка

### 8.1 Алгоритм

1. Все пары сортируются **по убыванию вероятности** совпадения (от наиболее похожих к наименее похожим).
2. Пары с вероятностью выше выбранного порога считаются "связанными" (ребро в графе).
3. Построение графа: профили — вершины, предсказания — рёбра.
4. Поиск **компонент связности** (Connected Components).
5. Каждая компонента связности = предсказанная entity.

**Сортировка по убыванию вероятности** гарантирует, что наиболее уверенные совпадения "склеивают" кластеры первыми, а слабые рёбра не разрушают уже сформированную структуру.

**Внимание к крупным entity:** для сущностей размером 8, 14, 19 профилей даже одно пропущенное ребро может разбить кластер на части. Возможна постобработка: если два кластера имеют высокое среднее сходство, они могут быть объединены.

### 8.2 Анализ ошибок

- **False Positives** (ложно объединённые профили): анализ причин, корректировка порога или доработка признаков.
- **False Negatives** (пропущенные дубликаты): проверка, не потеряны ли они на этапе blocking или meta-blocking. Если потеряны — расширение blocking-ключей.
- Отдельный анализ entity с 3+ профилями: все ли они корректно объединены в один кластер?

### 8.3 Пороги для production

| Уровень уверенности | Вероятность | Действие |
|---|---|---|
| Высокий | > 0.95 | **Автоматическое объединение** (перенос истории, бонусов) |
| Средний | 0.5 – 0.95 | **Ручная проверка** (отправка в интерфейс поддержки) |
| Низкий | < 0.5 | **Разные профили** (не объединяются) |

## 9. Демонстрационный интерфейс (Streamlit)

### 9.1 Функциональность MVP

- Загрузка батча профилей (CSV/JSON).
- Автоматический прогон через пайплайн: предобработка → блокировка → фичи → модель → кластеризация.
- Отображение найденных дубликатов с вероятностью совпадения.
- Рекомендация по объединению: "авто" / "ручная проверка".
- Визуализация: граф дубликатов, feature importance, explainability конкретной пары (какие признаки сработали).

### 9.2 Технологический стек интерфейса

- **Backend:** Python (FastAPI или прямой вызов в Streamlit).
- **Frontend:** Streamlit.
- **Визуализация графов:** NetworkX + Plotly.

## 10. Рекомендации по внедрению и масштабированию

### 10.1 Production-архитектура

```text
Новые события (поток)
│
▼
Kafka / очередь сообщений
│
▼
Сервис предобработки (нормализация, обогащение гео)
│
▼
Feature Store (хранение "золотых" профилей, Redis/PostgreSQL)
│
▼
Триггер пересчёта профиля → Blocking → Модель матчинга
│
▼
Кластеризация (батчевая, по расписанию)
│
▼
API для выдачи результатов (автообъединение / ручная проверка)
```

### 10.2 Мониторинг качества

- **Дрейф признаков:** отслеживание распределений ключевых признаков (email, телефон, имена) со временем.
- **Дрейф модели:** мониторинг доли автообъединений и ручных проверок.
- **Обратная связь:** логирование решений ручной проверки для дообучения модели (Active Learning).
- **Alerting:** алерт при резком падении доли автообъединений (возможна деградация модели).

### 10.3 Масштабирование

- **Blocking:** инвертированные индексы по blocking-ключам для быстрого поиска кандидатов.
- **Feature Engineering:** предварительное кэширование признаков профилей (email-домены, множества site_id).
- **Инкрементальное обновление:** при поступлении нового события пересчитывается только затронутый профиль, а не весь датасет.
- **Шардирование:** при росте до миллионов профилей — шардирование blocking-ключей по хэшу.

### 10.4 Ограничения MVP

- Не реализована потоковая обработка (только батчевый режим).
- Справочник гео-координат может отсутствовать (используется точное совпадение `geoname_id`).
- Крупные entity (14, 19 профилей) могут требовать ручной верификации даже при хорошем качестве модели.
